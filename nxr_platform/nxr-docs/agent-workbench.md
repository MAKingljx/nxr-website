# 子代理送评与逐卡归属

NXR 支持客户直接寄件，以及子代理代收客户卡片后集中寄件。子代理是 NXR 的下游送评渠道；每张卡始终保留原始客户和送评来源。

## 业务入口

- 送评工作台统一提供子代理管理、客户档案、来件库存、送评批次、客户回寄、企业额度和地址管理子菜单，地址为 `/nxr/submission-workbench/<view>`。
- NXR 平台：业务子菜单默认展示跨企业记录，支持搜索及进入对应企业处理；停用企业的历史记录仍可查看，企业额度汇总按企业展示 PTS 余额。子代理管理入口位于 `/nxr/submission-workbench/partners`。
- 子代理：相同业务菜单直接展示其绑定企业的信息，不提供跨企业选择或子代理管理入口。
- 企业筛选仅显示公司名称，切换业务子菜单保留企业，清除企业回到平台汇总。旧 `/nxr/partners` 和工作台 `?tab=...&company=...` 链接继续有效。
- 客户直寄：客户网站订单详情，在寄出前生成并打印逐卡收卡标签，并登记寄往 NXR 的物流。
- NXR 收件：后台订单管理支持包裹收件码及单卡收卡码查询；单卡查询展示原始客户、所属子代理、订单批次及回寄路线。

平台可一次开通企业及其独立后台登录账号，也可以为明确选定的现有企业增加后台账号。已有邮箱或用户名冲突会被拒绝，不按邮箱自动绑定其他身份。后台账号仅授予送评权限，不能访问平台全局客户、订单或确认自己的充值。

## 两条交接流程

1. 客户直寄：客户下单 → 按卡生成收卡标签 → 寄 NXR → NXR 清点、评级、封装 → 回寄客户。
2. 子代理合寄：客户寄子代理 → 子代理逐卡登记、贴收卡标签并清点 → 按客户来件生成批次与客户子单 → 合包寄 NXR → NXR 评级、封装 → 整包回子代理 → 核对后按原始客户回寄。

客户档案可归档，已有卡片仍保留历史及回寄能力。少件或有未解决异常的来件不能送评。NXR 主包裹的状态和子代理最后一段客户回寄分别记录。

## 每张卡的标识

- 直寄使用现有 `order_physical_item.barcode`；在客户主动准备标签时分配，重复准备保持同一码。
- 子代理使用已有 `agent_card.inventory_code`。新物理码沿用该收卡码；已有 NXR 物理码保留，通过订单卡片关系识别其别名。
- 一个客户的两张同名卡仍是不同的实物记录、不同收卡码。客户同名也不合并，归属依据客户、企业及订单项的明确关联。
- 收卡标签包含二维码、收卡编号、原始客户及客户编号、直寄或子代理来源、订单和序号。二维码只携带收卡码，不携带客户电话或完整地址。
- 收卡码用于入库；贴标和装箱继续使用当前导出的评级标签码及版本检查。评级证书编号后续关联到同一张卡。

`card-identities` 的 GET 只读取，POST 才为缺失项分配条码。分配不启动 NXR 工作会话，也不修改审核、付款和物流状态。扫码查询只能由有权限的 NXR 后台人员使用；子代理和客户只能读取自己的订单卡片。

## 资金和客户查询

企业送评使用统一 PTS 积分余额。线下充值先根据原币金额和已配置汇率生成积分快照，登记为待核款，平台财务确认实际收款后才增加积分；同一笔收款不能重复入账。送评付款仍需经过原有受理和条款确认，并核对当前积分报价后扣款；退款退回原扣款积分，不按新汇率重算。

默认 1 CNY = 1 PTS，其他支持币种初始未配置、未启用。平台在独立「企业额度设置」页配置比例和汇率。旧币种余额和历史流水继续保留，由平台财务预览折算、填写必填备注并明确确认后才能转为积分；升级不自动转换。具体流程、精确金额接口和迁移边界见 [企业统一积分额度](enterprise-credits.md)。

子代理可为单个客户子单生成、更新、复制或撤销私密只读查询链接。链接使用已配置的 `nxr.public-site.base-url` 与客户站 `/track/` 路由；更新使旧链接失效，撤销后无法查询。页面不会主动替用户发送链接。

物流节点目前由操作人员登记和确认，承运商自动查件接口仍使用项目现有配置边界。本次没有新增授信或子代理零售收款。

## 实现与迁移

工作台业务子菜单从服务端已授权路由整理生成，不扩大角色权限。平台汇总接口 `GET /api/admin/agent/overview/{view}` 实时检查无企业绑定、无限制数据范围及管理权限，额度额外检查财务权限；已有企业操作接口仍要求明确的企业范围。菜单整理本身不增加业务子菜单记录，独立企业额度设置菜单及积分数据结构由迁移 26 提供。

- `PartnerManagementService`：平台子代理列表、资料、后台开通、线下充值登记及幂等记录。
- `AgentOperatorScopeService`：后台用户与企业绑定及实时权限校验，保留原有内部角色键。
- `AgentWorkbenchService`：客户来件、库存、照片、原子送评和客户回寄。
- `EnterpriseCreditService`：全局积分比例、币种汇率、报价快照及历史余额显式转换。
- `MerchantWalletService`：企业积分充值、扣款、退款及原有货币流水保留。
- `OrderCardIdentityService`：直寄与子代理的统一归属查询、条码分配和 NXR 扫码定位。
- `OrderWorkbenchService`：入库码别名解析及既有评级标签版本、装箱校验。
- `nxr-frontend-shared/cardLabels.ts`：两个前端共用的无状态标签打印视图，由各自前端提供二维码编码器，构建后随各自资源发布。

依次执行迁移 23、24、25、26。迁移 25 增加平台管理菜单、更新工作台显示名称与路由，并增加管理操作记录表，不重编号既有卡片或自动绑定真实账号。迁移 26 必须在启用积分版后端前执行，新增积分设置、汇率、快照和转换记录表以及独立设置菜单，不自动转换历史余额。已有数据库须核对环境后增量迁移，不能为升级重跑初始化脚本。生产数据变更另行确认，Python 的 `Data/` 不在本功能变更范围。

## 本地验收

使用专门的 `nxr_acceptance_agent_*` 数据库和 8090 回环后端。准备脚本拒绝覆盖已有数据库，验收脚本通过价格标记核对实例后才创建合成记录；支付提供商及邮件保持关闭。

```bash
python3 nxr-scripts/prepare-agent-workbench-qa.py --database nxr_acceptance_agent_example --apply
# 启动指向该库的本地 QA 后端后：
NXR_QA_DATABASE=nxr_acceptance_agent_example python3 nxr-scripts/verify-agent-workbench.py
NXR_QA_DATABASE=nxr_acceptance_agent_example python3 nxr-scripts/verify-partner-card-identities.py
```

验证涵盖后台权限与企业隔离、并发开通/充值、财务核款、同名客户与同名卡、条码重复分配稳定、直寄和子代理归属、旧码别名、标签版本防绕过，以及现有审核付款至回寄签收流程。浏览器预览使用原生窗口尺寸，不固定测试视口。
